基于Yolov8-seg的视觉分割首次尝试

发表于2026-10-14|发生于2026-10-22|指间世界
|浏览量:

从一段监控视频到一个能用的分割模型：完整训练流程记录

最近在做「投料口有料占比检测」，需求其实很朴素：摄像头对着投料口拍，程序实时算出料堆占了百分之多少，然后把数值报给 PLC。

听起来是个标准的分割任务，但真正做下来，坑基本不在模型上，而在怎么把斜着拍的画面整理成模型能学的样子。这篇把整条流水线从头到尾记一遍。

1 先说清楚要干什么

摄像头装在侧上方，拍到的投料口是个斜着的梯形，而且带透视畸变。直接拿这种图去训练，模型要同时学”什么是料”和”这个梯形怎么摆”，难度翻倍。

所以思路是：先把画面拉正，再让模型学。

最终定下来的方案：

  • 透视校正，把斜视的投料口拉成一个规规矩矩的 800×600 矩形
  • 用 YOLOv8-seg 做实例分割，只分一类：material（料）
  • 推理时算出 mask 像素占整幅图的百分比，就是”有料占比”

2 整体流程

一共 11 个脚本，全放在 tools/ 目录下，按顺序编号，跑一遍就出结果。

3 逐步骤拆解

3.1 抽帧

从现场录的视频里按固定间隔抽图片。

采样率不用高，我设的是几秒一帧——视频里相邻帧几乎一样，抽太密除了增加标注量没别的作用。最后攒下几百张，覆盖不同的料位状态就够。

输出文件名从 02000 开始编号。

3.2 标定四个角（只做一次）

这个是整条流水线里唯一需要人工介入的几何环节。

写了个交互脚本：弹出一张参考帧，用鼠标依次点投料口的四个角，按 s 保存。脚本会把坐标还原回原始分辨率，存成 roi_calib.json。

这一步只需要做一次，除非摄像头被碰过位置或换了镜头。后面所有帧都复用这份标定。

提醒：标定点的选择直接决定后面所有步骤的成败。四个点要贴在投料口真实边界上，宁可稍微往外扩一点，也别切在料堆经常出现的区域里面。

3.3 透视校正（核心）

读标定文件，对每一帧做 warpPerspective，输出固定 800×600。

这里有个小细节值得记一下：脚本里会自动给四个角排序，所以标定时点错顺序也没关系。排序用的是经典的 order_points 方法——按 x+y 找左上/右下，按 y-x 找右上/左下。

就是这一行公式，后来在 C++ 部署端埋了个大坑（后面第五节说）。

输出尺寸 800×600 是拍脑袋定的吗？部分是。我后来拿标定数据反推了一下投料口的真实长宽比，大约是 1.8:1，而 800×600 是 1.33:1——也就是说画面其实被纵向拉伸了不少。

但我最后没改。原因是：训练数据就是这么产出的，模型已经”习惯”了这个变形。改掉反而会破坏训练和推理的一致性。

这个点挺反直觉的：几何上”更正确”的做法，在工程上可能是错的。训练和推理必须同源，这比画面比例漂不漂亮重要得多。

3.4 人工标注

用 X-AnyLabeling 画多边形，类别只写一个：material。

没料的图一张都不画，保持空标注。这些空样本是负样本，对抑制误检很关键——不然模型看到什么都想框一下。

3.5 补空标注 + 重排序号

有个小麻烦：标注工具对”没画任何东西”的图片不生成 json 文件，但后面的脚本要求每张图必须有对应的 json。所以先写个脚本把缺的补上空 json。

然后写脚本把图片和 json 一起重排成连续序号（00000、00001……）。这里用了两阶段改名（先改成临时名再改成最终名），避免中途名字撞车把文件覆盖掉。

3.7 划分训练集和验证集

按大约 8:2 划分。

有个特意做的处理：验证集里固定放几张空样本。因为空样本数量本来就不多，随机分的话验证集可能一张都没有，这样验证指标会失真——模型在有料的图上表现好，但根本没验证过它会不会在空场景下乱框。

3.8 训练

基础模型用 yolov8n-seg.pt（预训练），参数很常规：150 轮，输入 640，batch 8，GPU 单卡。数据增强基本用 ultralytics 的默认配置。

训练跑完，验证集上 mask 的 mAP50 到了 0.95 左右，mAP50-95 在 0.7 上下。

这个数字其实挺关键的——它说明模型本身学得不错。后来现场效果差，问题不在模型。

3.9 视频验证

两个验证脚本，思路一样：读视频 → 逐帧透视校正 → 推理 → 把 mask 叠上去 → 算占比。

为了省时间，不是每帧都推理，而是每 N 帧推理一次，中间帧复用上一次的结果。实测下来视觉上完全够用，毕竟料位变化是慢过程。

其中一个脚本做的是左右分屏：左边原始视频，右边校正+mask，中间一条白线隔开，再叠加占比数字和时间戳。这个拿去给现场看最直观。

另一个会输出 CSV，每几秒记一条时间和占比，可以直接画曲线看趋势。

3.10 导出部署

导出 ONNX，固定输入尺寸，opset 给到 17（OpenCV DNN 读 ONNX 需要够高的 opset）。

然后拷到程序的 assets/ 目录下，C++ 端加载。

4 几个容易踩的坑

1. 标注和推理的预处理必须一模一样

这是整个项目最大的教训。我在 C++ 端部署后发现分割效果明显不如 Python 验证时——框不准、mask 糊。

查下来是四处不一致，其中两处致命：

  • 多了一步旋转：C++ 端在透视校正后额外做了 90° 旋转。但训练数据和 Python 验证脚本里全程没有任何旋转。模型训练时从没见过这个朝向，等于喂了个没见过的东西进去。
  • letterbox 的填充方式不对：YOLO 的 letterbox 是等比缩放后两侧均分灰色填充（灰值 114），我 C++ 端写成了左上角对齐、右下角补黑边。800×600 缩到 640×640 时上下各有 80 像素灰边，这么一错，mask 反算回原图位置整整偏了 100 像素。

另外两处是 NMS 的 IoU 阈值和 mask 坐标反算的起点，也都对齐了。

教训：训练时怎么预处理，推理时必须一字不差地照抄。模型学到的是”这个分布下的规律”，分布一变，精度立刻崩。

2. 几何上的”正确”未必是工程上的”正确”

前面说的画面拉伸问题就是典型。1.8:1 拉成 1.33:1，看起来是错的，但因为训练和推理都这么拉，模型反而适应得很好。如果只改推理端，精度只会更差。

3. 验证脚本之间的参数要统一

我两个验证脚本的置信度阈值不一样（一个 0.1 一个 0.25），导致两个脚本跑出来的占比数字对不上，排查时绕了弯路。这种常量要么写进配置，要么至少保持一致。

4. 正负样本都要有

空样本一定要留。全是有料的图训出来的模型，遇到空场景大概率会框出点什么来。

5 最后

整条流水线跑通之后回头看，真正花时间的不是调模型，而是：

  • 把数据整理成”模型好学的样子”（透视校正占了大半功劳）
  • 保证训练和推理的每一个预处理步骤严格一致

模型结构、超参数这些反而是最省心的部分——YOLOv8-seg 的默认配置在这个任务上就够用了。

如果再来一次，我会在写 C++ 推理端之前，先把训练侧的每一步预处理单独拎出来、存成可视化中间结果，部署时逐个像素比对。这比事后靠”看起来不对”去猜要高效得多。
